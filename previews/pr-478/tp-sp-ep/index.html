大模型推理中的 TP-SP-EP 混合并行优化¶

在大模型训练中，单纯的张量并行（TP）或序列并行（SP）往往难以覆盖所有层的通信需求。对于稠密的 Attention 层，TP 可以高效地切分权重矩阵；而对于 MoE 层，专家并行（EP）才是降低通信开销的关键。本文梳理一种将 TP、SP、EP 融合的混合并行策略——重点剖析 Attention 层的三种输出投影路径，以及 MoE 层的 Dispatch / Combine 机制，帮助理解它们如何协同工作以最大化吞吐。

一、三种混合并行图示¶

TP / SP / EP 总览图

上面的总览图展示了 Attention 层的三条输出投影路径。三条路径都从同一个列并行 qkv_linear 出发，区别在于如何处理输出投影：方案一走行并行 + all_reduce + slice，方案二走行并行 + reduce_scatter，方案三走 all2all + 完整权重。后续的 MoE 层则统一以 SP 排布作为输入，借助两次 all2all 完成专家路由与聚合。

二、并行原理解析¶

三条方案的起点相同：列并行的 qkv_linear 将输出激活按隐藏层维度切分分布在各 GPU 上。从这一状态出发，三条路径以不同方式完成 out_linear 并进入序列并行段。

2.1 前提：qkv_linear (列切)¶

三种方案都始于一个列并行 (Column-Parallel) 的 qkv_linear 层。

  • 我们有 NNN 个 GPU。
  • 输入 XXX 是复制的 (replicated)。
  • 第一个 qkv_linear 层的权重 AAA 被按列切分：A=[A1,A2,…,AN]A = [A_1, A_2, \dots, A_N]A=[A1​,A2​,…,AN​]。
  • GPU iii 计算：Yi=GeLU(XAi)Y_i = \text{GeLU}(X A_i)Yi​=GeLU(XAi​)。
  • 关键状态：计算完成后，中间激活 Y=[Y1,…,YN]Y = [Y_1, \dots, Y_N]Y=[Y1​,…,YN​] 在 NNN 个 GPU 上是按隐藏层维度（HdimH_{\text{dim}}Hdim​ 维度，也常称为 KKK 维度）切分的。

这里涉及到 Attention 的 TP 并行，原理可参考猛猿大佬文章 https://zhuanlan.zhihu.com/p/622212228，不再赘述。现在，我们要计算第二层 Z=YWZ = YWZ=YW，其中 WWW 是 out_linear 的权重。

此时有三条路可走：方案一先 all_reduce 再切成 SP shard，方案二直接用 reduce_scatter 落到 SP shard，方案三则提前通信将切分轴转到序列维度。

2.2 方案一：out_linear (行切) + all_reduce + Slice¶

这个方案的核心思想是保持 HdimH_{\text{dim}}Hdim​ 维度的切分。

  1. 数据排布：
    • 输入（YYY）：Y=[Y1,…,YN]Y = [Y_1, \dots, Y_N]Y=[Y1​,…,YN​]（按 HdimH_{\text{dim}}Hdim​ 切分）。
    • 权重（WWW）：out_linear 权重 WWW 必须同样按 HdimH_{\text{dim}}Hdim​ 维度（即行）切分： W=[W1W2⋮WN]W = \begin{bmatrix} W_1 \\ W_2 \\ \vdots \\ W_N \end{bmatrix}W=​W1​W2​⋮WN​​​
  2. out_linear（局部计算）：
    • GPU iii 拥有 YiY_iYi​ 和 WiW_iWi​。
    • 它只能计算它所拥有的那部分乘积：Zi=YiWiZ_i = Y_i W_iZi​=Yi​Wi​。
  3. all_reduce（通信）：
    • 根据矩阵乘法，最终结果是 Z=YW=∑i=1NYiWiZ = YW = \sum_{i=1}^N Y_i W_iZ=YW=∑i=1N​Yi​Wi​。
    • all_reduce 操作在所有 GPU 之间对 ZiZ_iZi​ 进行求和。
    • AllReduce({Z1,…,ZN})→Z\text{AllReduce}(\{Z_1, \dots, Z_N\}) \to ZAllReduce({Z1​,…,ZN​})→Z。
  4. 得到完整的 ZZZ：
    • ZZZ 在所有 GPU 上都是完整的、复制的 (replicated)。
  5. 每张 GPU 从 ZZZ 的行维度平均 Slice 出一部分，转为序列并行送到下一层。

  • 如果下一跳只需要本 rank 的 SP shard，那么这一步可以进一步升级成方案二里的 reduce_scatter，不必先拿到完整 ZZZ 再切片；第 3 节会单独比较。

  • 优点：

    • 节省内存：每个 GPU 只需要存储 1/N1/N1/N 的 WWW 权重。这在权重（如 WprojW_{\text{proj}}Wproj​）非常大时至关重要。

  • 缺点：

    • 通信瓶颈：必须在计算 ZiZ_iZi​ 之后执行一个 all_reduce。这是一个同步操作，通信量为 ZZZ 的大小，可能会阻塞流水线。

2.3 方案二：out_linear (行切) + reduce_scatter¶

这个方案延续了方案一的行并行权重切分，只是把“先 all_reduce 得到完整 ZZZ、再本地切片”的两步操作收敛成一次 reduce_scatter。

  1. 数据排布：
    • 输入（YYY）：Y=[Y1,…,YN]Y = [Y_1, \dots, Y_N]Y=[Y1​,…,YN​]（按 HdimH_{\text{dim}}Hdim​ 切分）。
    • 权重（WWW）：out_linear 权重 WWW 仍按 HdimH_{\text{dim}}Hdim​ 维度（即行）切分： W=[W1W2⋮WN]W = \begin{bmatrix} W_1 \\ W_2 \\ \vdots \\ W_N \end{bmatrix}W=​W1​W2​⋮WN​​​
  2. out_linear（局部计算）：
    • GPU iii 拥有 YiY_iYi​ 和 WiW_iWi​。
    • 它先计算局部部分结果：Zi=YiWiZ_i = Y_i W_iZi​=Yi​Wi​。
  3. reduce_scatter（通信 + 归约）：
    • reduce_scatter 会一边对各卡的 ZiZ_iZi​ 求和，一边把结果沿 sequence 维切分后分发到不同 GPU。
    • GPU jjj 最终直接拿到自己的 SP shard： ZjSP∈R(S/N)×HdimZ_j^{\text{SP}} \in \mathbb{R}^{(S/N) \times H_{\text{dim}}}ZjSP​∈R(S/N)×Hdim​
  4. 最终结果：
    • 输出不再是 replicated 的完整 ZZZ，而是已经按序列维度切分好的 SP 排布。
  • 优点：
    • 通信量减半：相比方案一的 all_reduce + slice，集合通信从两段收敛为一段。
    • 仍然节省权重内存：每个 GPU 依旧只需要存储 1/N1/N1/N 的 WWW 权重。
  • 缺点：
    • 重叠空间仍有限：和方案一一样，它仍然必须等待本地 out_linear 计算出 ZiZ_iZi​ 之后才能启动集合通信。

2.4 方案三：all2all + out_linear (不切分)¶

这是“张量并行（TP）切换到序列并行（SP）”的策略。这个方案的核心思想是通过通信改变数据的切分维度。

  1. 数据排布：
    • 输入（YYY）：Y=[Y1,…,YN]Y = [Y_1, \dots, Y_N]Y=[Y1​,…,YN​]（按 HdimH_{\text{dim}}Hdim​ 切分）。
    • 权重（WWW）：out_linear 权重 WWW 不切分（replicated）。每个 GPU 都有完整的 WWW。
  2. all2all（通信）：
    • 这一步的目标是将 YYY 的数据排布从“按 HdimH_{\text{dim}}Hdim​ 切分”转置为“按序列（Sequence）维度切分”。
    • 之前：GPU iii 拥有 YiY_iYi​（形状 S×(Hdim/N)S \times (H_{\text{dim}}/N)S×(Hdim​/N)）。
    • 操作：
      • GPU iii 将它的 YiY_iYi​ 沿着 SSS 维度切成 NNN 块：Yi=[Yi(1)T,…,Yi(N)T]TY_i = [Y_i^{(1)T}, \dots, Y_i^{(N)T}]^TYi​=[Yi(1)T​,…,Yi(N)T​]T。
      • GPU iii 将 Yi(j)Y_i^{(j)}Yi(j)​ 发送给 GPU jjj。
      • GPU jjj 收到来自所有 NNN 个 GPU 的 {Y1(j),…,YN(j)}\{Y_1^{(j)}, \dots, Y_N^{(j)}\}{Y1(j)​,…,YN(j)​}。
    • 之后：GPU jjj 将收到的块沿着 HdimH_{\text{dim}}Hdim​ 维度拼接起来（⚠️：这里会有一个 transpose 操作），得到 Y^j=[Y1(j),…,YN(j)]\hat{Y}_j = [Y_1^{(j)}, \dots, Y_N^{(j)}]Y^j​=[Y1(j)​,…,YN(j)​]（形状 (S/N)×Hdim(S/N) \times H_{\text{dim}}(S/N)×Hdim​）。
    • 结果：YYY 的排布从 NNN 个 S×(K/N)S \times (K/N)S×(K/N) 的块（TP）转换成了 NNN 个 (S/N)×K(S/N) \times K(S/N)×K 的块（SP）。
  3. out_linear（局部计算）：
    • GPU jjj 拥有 Y^j\hat{Y}_jY^j​（形状 (S/N)×Hdim(S/N) \times H_{\text{dim}}(S/N)×Hdim​）和完整的 WWW（形状 Hdim×HdimH_{\text{dim}} \times H_{\text{dim}}Hdim​×Hdim​）。
    • 它计算 Zj=Y^jWZ_j = \hat{Y}_j WZj​=Y^j​W。
  4. 最终结果：
    • ZjZ_jZj​ 的形状是 (S/N)×Hdim(S/N) \times H_{\text{dim}}(S/N)×Hdim​。
    • 最终输出 ZZZ 在 NNN 个 GPU 上是按序列（Sequence）维度切分的。

在工程实现上，它们对应三种不同的取舍：

特性方案一 (all_reduce + slice)方案二 (reduce_scatter)方案三 (all2all + 完整权重)
策略标准行并行，先聚合再切片标准行并行，直接归约到 SP shard张量并行 (TP) →\to→ 序列并行 (SP) 转换
out_linear 权重 WWW按行切分 (节省 N−1/NN-1/NN−1/N 内存)按行切分 (节省 N−1/NN-1/NN−1/N 内存)不切分/复制 (需要 NNN 倍内存)
通信操作all_reduce + 本地 slicereduce_scatterall2all
通信发生时机out_linear 之后out_linear 之后out_linear 之前
通信内容输出 ZZZ (形状 S×HdimS \times H_{\text{dim}}S×Hdim​)输出 ZZZ (形状 S×HdimS \times H_{\text{dim}}S×Hdim​)激活 YYY (形状 S×HdimS \times H_{\text{dim}}S×Hdim​)
输出 ZZZ 的排布先复制，再本地切成 SP按序列切分 (Sequence-Parallel)按序列切分 (Sequence-Parallel)

结论是：方案二在不改变权重切分方式的前提下，把方案一的 all_reduce + slice 收敛为 reduce_scatter，通信量减半；方案三则进一步牺牲 WWW 的内存（现在需要 NNN 份 WWW），换取把并行维度从 HdimH_{\text{dim}}Hdim​（TP）切换到 SSS（SP），并利用更靠前的 all2all 通信来提升流水线效率。

三、通信量对比分析¶

通信量是决定这些方案性能的关键因素。为了避免混淆，下面统一采用每个 GPU 的单向发送量作为统计口径，也就是：

  • 只统计每个 GPU 发出去多少字节
  • 不重复累计接收量
  • 避免把 all_reduce 的“两阶段”和 all2all 的“发送+接收”混在一起

先定义统一记号：

  • NNN：并行数
  • SSS：序列长度（或 token 数）
  • HdimH_{\text{dim}}Hdim​：隐藏层维度
  • ddd：每个元素的字节数
  • 定义完整输出张量大小为：
M=S×Hdim×dM = S \times H_{\text{dim}} \times dM=S×Hdim​×d

3.1 方案一：out_linear (行切) + all_reduce + slice¶

在该方案中，每个 rank 先计算自己的 partial result：

Zi∈RS×HdimZ_i \in \mathbb{R}^{S \times H_{\text{dim}}}Zi​∈RS×Hdim​

然后通过 all_reduce 得到完整的 ZZZ，最后再按 sequence 维切出本 rank 需要的 SP shard。

这里通信对象是 ZiZ_iZi​，大小为：

M=S×Hdim×dM = S \times H_{\text{dim}} \times dM=S×Hdim​×d

对 ring all-reduce 而言，它可以拆成两段：

  1. reduce-scatter
  2. all-gather

每一段的单向发送量都是：

N−1N⋅M\frac{N-1}{N} \cdot MNN−1​⋅M

因此，方案一的每 GPU 单向发送总量为：

VAR=2⋅N−1N⋅MV_{AR} = 2 \cdot \frac{N-1}{N} \cdot MVAR​=2⋅NN−1​⋅M

3.2 方案二：out_linear (行切) + reduce_scatter¶

如果下一跳只需要 SP shard，那么没有必要先得到完整 ZZZ 再切片，可以直接对 ZiZ_iZi​ 做 reduce_scatter：

reduce_scatter(Zi)\text{reduce\_scatter}(Z_i)reduce_scatter(Zi​)

此时每个 rank 直接拿到自己的 SP shard。

注意，这里通信对象仍然是 ZiZ_iZi​，大小仍然是：

M=S×Hdim×dM = S \times H_{\text{dim}} \times dM=S×Hdim​×d

对应的每 GPU 单向发送量为：

VRS=N−1N⋅MV_{RS} = \frac{N-1}{N} \cdot MVRS​=NN−1​⋅M

因此，相比方案一：

VRSVAR=12\frac{V_{RS}}{V_{AR}} = \frac{1}{2}VAR​VRS​​=21​

也就是说，方案二的 reduce_scatter 相比方案一的 all_reduce + slice，通信量减半，减少 50%。

3.3 方案三：all2all + out_linear (不切分)¶

方案三的目标是先把激活的切分方式从 hidden 维（TP）转为 sequence 维（SP）。

设每个 rank 上本地激活为：

Yi∈RS×(Hdim/N)Y_i \in \mathbb{R}^{S \times (H_{\text{dim}}/N)}Yi​∈RS×(Hdim​/N)

在 all2all 中，每个 rank 将 YiY_iYi​ 沿 sequence 维切成 NNN 块，每块大小为：

SN×HdimN\frac{S}{N} \times \frac{H_{\text{dim}}}{N}NS​×NHdim​​

每个 rank 保留其中 1 块，并把其余 N−1N-1N−1 块分别发送给其他 N−1N-1N−1 个 rank。

因此，每块数据大小为：

MN2\frac{M}{N^2}N2M​

每个 rank 一共发送 N−1N-1N−1 块，所以总单向发送量为：

VA2A=(N−1)⋅MN2=N−1N2⋅MV_{A2A} = (N-1) \cdot \frac{M}{N^2} = \frac{N-1}{N^2} \cdot MVA2A​=(N−1)⋅N2M​=N2N−1​⋅M

3.4 三种通信方案的统一口径对比¶

统一按每 GPU 单向发送量统计，把三种方案放在一起：

方案通信操作每 GPU 单向发送量
方案一all_reduce + sliceVAR=2⋅N−1N⋅MV_{AR} = 2 \cdot \frac{N-1}{N} \cdot MVAR​=2⋅NN−1​⋅M
方案二reduce_scatterVRS=N−1N⋅MV_{RS} = \frac{N-1}{N} \cdot MVRS​=NN−1​⋅M
方案三all2allVA2A=N−1N2⋅MV_{A2A} = \frac{N-1}{N^2} \cdot MVA2A​=N2N−1​⋅M

比例关系也就非常清晰了：

  1. 方案二 vs 方案一：
VRSVAR=12\frac{V_{RS}}{V_{AR}} = \frac{1}{2}VAR​VRS​​=21​

说明方案二的 reduce_scatter 相比方案一的 all_reduce + slice，通信量减少 50%。

  1. 方案三 vs 方案二：
VA2AVRS=1N\frac{V_{A2A}}{V_{RS}} = \frac{1}{N}VRS​VA2A​​=N1​

说明方案三的 all2all 通信量是方案二 reduce_scatter 的 1/N1/N1/N，也就是相比方案二还要再少 NNN 倍。

  1. 方案三 vs 方案一：
VA2AVAR=12N\frac{V_{A2A}}{V_{AR}} = \frac{1}{2N}VAR​VA2A​​=2N1​

说明方案三的 all2all 通信量是方案一 all_reduce + slice 的 1/(2N)1/(2N)1/(2N)。

以 N=4N=4N=4 为例：

VAR=2⋅34⋅M=32MV_{AR} = 2 \cdot \frac{3}{4} \cdot M = \frac{3}{2}MVAR​=2⋅43​⋅M=23​M VRS=34MV_{RS} = \frac{3}{4}MVRS​=43​M VA2A=316MV_{A2A} = \frac{3}{16}MVA2A​=163​M

因此：

  • 方案二的 reduce_scatter 相比方案一的 all_reduce + slice，通信量减少 50%
  • 方案三的 all2all 相比方案二的 reduce_scatter，通信量只有 1/4，也就是减少 75%
  • 方案三的 all2all 相比方案一的 all_reduce + slice，通信量只有 1/8

除此之外，选择方案三还有其他的工程原因：

  1. 通信模式：all_reduce 包含计算（Sum），而 all2all 只是数据交换（Transpose）。在某些硬件拓扑（如 NVLink Switch）上，all2all 几乎可以达到线速，效率极高。
  2. 通信重叠：方案三的 all2all 作用于 YYY，它可以在 YYY 被计算时重叠 (Overlap) 进行。方案一和方案二的集合通信都必须等待 out_linear 计算 ZiZ_iZi​ 完成后才能开始。
  3. 内存代价：方案三的优势是有代价的。它需要每个 GPU 都存储完整的 out_linear 权重 WWW，而方案一和方案二都只需要 1/N1/N1/N 的权重。
  4. 序列并行 (SP)：如果你的网络架构（例如 MoE EP 并行）被优化为在序列并行的输入上工作，那么方案三的输出（ZZZ 按序列切分）可以直接喂给下一层，完全消除了后续对 ZZZ 进行 all_reduce 或 allgather 的需求。

3.5 为什么说方案三里的 all2all 更容易和前面的计算重叠？¶

这里的“更容易重叠”，并不是说 all2all 天生就一定能自动 overlap，而是说：它的通信位置更靠前，依赖更早暴露出来，粒度上也更容易做成流水。

先看三种方案的关键区别：

  • 方案一：行并行 out_linear + all_reduce
    • 先在每张卡上做本地部分计算，得到 Zi=YiWiZ_i = Y_i W_iZi​=Yi​Wi​
    • 然后再通过 all_reduce 把各卡的部分结果求和，得到完整输出 Z=∑iYiWiZ = \sum_i Y_i W_iZ=i∑​Yi​Wi​
  • 方案二：行并行 out_linear + reduce_scatter
    • 同样先在每张卡上完成本地部分计算，得到 Zi=YiWiZ_i = Y_i W_iZi​=Yi​Wi​
    • 然后通过 reduce_scatter 在归约的同时，直接把结果切成各卡所需的 SP shard
  • 方案三：先 all2all，把 TP 排布转成 SP 排布，再做完整权重的 out_linear
    • 先对 YYY 做一次 all2all，把数据从“按 hidden 维切分”转换为“按 sequence 维切分”
    • 转换后，每张卡拿到本地的一段完整 hidden 激活 Y^j\hat{Y}_jY^j​
    • 然后每张卡独立做完整的 out_linear

这里最大的区别在于：

  • 方案一和方案二通信的，都是 out_linear 之后的结果 ZiZ_iZi​
  • 方案三通信的是 out_linear 之前的激活 YYY

也就是说，方案三里的 all2all 发生在更靠前的位置，而方案一和方案二的集合通信都发生在更靠后的位置。

这里说的“前面的计算”，主要是指 Attention 侧产出 YYY 的那部分计算，也就是：

  • qkv_linear
  • attention 计算本身
  • 必要的 reshape / pack / transpose

在 TP 场景下，每张卡拿到的是自己本地的一份激活：

Yi∈RS×HdimNY_i \in \mathbb{R}^{S \times \frac{H_{\text{dim}}}{N}}Yi​∈RS×NHdim​​

如果采用方案三，那么每张卡会把本地的 YiY_iYi​ 再按 sequence 切成更小的块，然后通过 all2all 发给不同 GPU。接收端把来自各卡的块沿 hidden 维拼起来，形成自己本地需要处理的：

Y^j∈RSN×Hdim\hat{Y}_j \in \mathbb{R}^{\frac{S}{N} \times H_{\text{dim}}}Y^j​∈RNS​×Hdim​

之后再在本地执行完整权重的 out_linear。

更准确地说，方案三里的 all2all 主要有两类 overlap 机会。

1. 和 YYY 的生成过程重叠¶

如果 YYY 不是一次性全部算完才可用，而是可以按 chunk、tile、token block 逐步产出，那么就可以这样做：

  • 计算流继续生成后续的 YYY chunk
  • 通信流把前面已经 ready 的 YYY chunk 立刻拿去做 all2all

也就是说，可以做到：

一边继续算后面的 YYY，一边把前面已经算好的 YYY 发出去

这是最核心的一层 overlap。它之所以能成立，是因为方案三里通信对象就是 YYY 本身，通信发生在 out_linear 之前，所以只要某一部分 YYY 已经 ready，这部分就可以尽早进入通信。

2. 和接收侧的 out_linear 计算重叠¶

接收端 GPU 在收到一部分 all2all 数据后，如果实现足够细粒度，也不一定要等全部数据都到齐才开始算。完全可以做到：

  • 通信流继续接收后续 chunk
  • 计算流对已经到齐并拼好的那部分 Y^\hat{Y}Y^ 先执行本地 out_linear

于是就形成了：

前面块继续传，后面块已经开始算

这就把整个过程做成了一个更细粒度的流水线：

生成 YYY → 交换 YYY → 计算 out_linear

可以把方案三直观理解成下面这条流水线：

为什么 all_reduce 更难和“前面的计算”重叠？核心原因主要有两个。

1. 依赖更晚¶

在方案一里，all_reduce 的输入不是 YYY，而是：

Zi=YiWiZ_i = Y_i W_iZi​=Yi​Wi​

也就是说，必须先做完 out_linear，得到部分结果 ZiZ_iZi​，才能开始 all_reduce。

所以它的依赖链是：

先生成 YYY → 再做 out_linear → 最后 all_reduce

而不是像方案三那样：

生成 YYY 的同时，就可以逐步开始通信

换句话说，all_reduce 的通信起点更晚，天然就少了一段 overlap 窗口。

2. all_reduce 带归约语义，流水化更受限制¶

all2all 本质上是数据交换，你把该发的块发出去即可；但 all_reduce 不只是传数据，还需要做归约（例如求和），所以通信和归约语义是绑定在一起的。

这并不是说 all_reduce 完全不能 overlap。实际上，很多实现里的 ring all_reduce 也会按 chunk 做流水，甚至也能和部分计算重叠。但相比 all2all 这种纯交换，all_reduce 通常更难做成那种“上游一边生产、下游一边持续消费”的干净流水。

四、EP 并行的 MoE 层¶

无论选择方案一、方案二还是方案三，进入 MoE 层前激活最终都已处于序列并行（SP）的排布——方案一靠本地 slice，方案二靠 reduce_scatter，方案三则在 all2all 后天然转成 SP。此时每张 GPU 持有全局序列的 1/P1/P1/P 片段，形状为 SP×Hdim\frac{S}{P} \times H_{\text{dim}}PS​×Hdim​。EP 的核心思想是将专家参数分片到各 GPU，同时通过两次 all2all 完成 token 的路由与聚合，以此避免所有 GPU 都冗余存储全量专家权重。

MoE Dispatch / Combine 路由图

4.1 假设一些参数：¶

  • 输入：X∈RS×HdimX \in \mathbb{R}^{S \times H_{\text{dim}}}X∈RS×Hdim​
  • Router：为每个 token 选 kkk 个专家（Top-k），得到
    • 专家索引：eid∈{0,…,E−1}S×k\text{eid} \in \{0,\dots,E-1\}^{S \times k}eid∈{0,…,E−1}S×k
    • 权重：w∈RS×kw \in \mathbb{R}^{S \times k}w∈RS×k
  • 专家集合：共有 EEE 个 experts
  • EP 规模：PPP（同一个 EP group 中有 PPP 张 GPU）
    • 每张 GPU 持有 E/PE/PE/P 个 experts（参数分片）

两次 all2all（Dispatch / Combine）：

EP 的本质是：按专家维度切参数，但按 token 路由把激活在卡间重排。因此每个 MoE 层固定两次集合通信。

  • Dispatch：把 token 送到“持有目标专家”的 GPU
  • Combine：把专家输出送回“token 所在的 GPU”，并按权重聚合

MoE 输入的 SP 排布：

  • 全局 SSS 个 tokens，被 PPP 张 GPU 按序列维度均分
    • GPU iii 拥有：Xi∈RSP×HdimX_i \in \mathbb{R}^{\frac{S}{P} \times H_{\text{dim}}}Xi​∈RPS​×Hdim​
  • 每个 GPU 本地计算 Router：
    • eidi∈{0,…,E−1}SP×k\text{eid}_i \in \{0,\dots,E-1\}^{\frac{S}{P} \times k}eidi​∈{0,…,E−1}PS​×k
    • wi∈RSP×kw_i \in \mathbb{R}^{\frac{S}{P} \times k}wi​∈RPS​×k

4.2 Dispatch：permute + all2all（把 token 发到专家所在卡）¶

目标：将 token 从“按序列切分”的排布，变换为“按专家分桶并落在对应 GPU”的排布。

本地分桶（bucketize）/ 打包（pack）：

  • 对 GPU iii 上的每个 token ttt，它会被路由到 kkk 个专家：eidi[t,1],…,eidi[t,k]{\text{eid}_i[t,1], \dots, \text{eid}_i[t,k]}eidi​[t,1],…,eidi​[t,k]
  • 定义专家到 GPU 的映射（静态）：
    • owner(e)∈{0,…,P−1}\text{owner}(e) \in \{0,\dots,P-1\}owner(e)∈{0,…,P−1}
  • GPU iii 将其本地 token 复制出 kkk 份“token-expert 关联样本”，并按 owner(e)\text{owner}(e)owner(e) 分桶：
    • 形成 PPP 个发送缓冲区：sendbufi→j\text{sendbuf}_{i\to j}sendbufi→j​
  • 同时，GPU iii 记录两类索引用于还原：
    • src_slot：这个样本来自本地第几个 token
    • k_slot：这是 top-k 的第几路（用于乘权重）

第一次 all2all：

  • 所有 GPU 同时执行 all2all，recvbufj=⋃i=0P−1sendbufi→j\text{recvbuf}_{j} = \bigcup_{i=0}^{P-1} \text{sendbuf}_{i\to j}recvbufj​=⋃i=0P−1​sendbufi→j​

Dispatch 后的数据排布：

  • GPU jjj 得到按其本地 experts 分桶后的激活集合：
    • X^j∈RMj×Hdim\hat{X}_j \in \mathbb{R}^{M_j \times H_{\text{dim}}}X^j​∈RMj​×Hdim​
  • 其中 MjM_jMj​ 是路由到 GPU jjj 的（token, expert）样本数（一般不均匀）。
  • 同时携带对应的还原元信息（如 src_slot / k_slot、以及回传路由所需的 index）。

关键状态：Dispatch 后，激活不再保持原序列顺序，而是按专家分桶组织，便于专家侧批处理。

4.3 Experts：本地 grouped_gemm（只在持有的专家上算）¶

GPU jjj 持有专家集合，每个专家是一个 FFN：

  • Expert eee 的参数：W1(e),W2(e)W^{(e)}_1, W^{(e)}_2W1(e)​,W2(e)​
  • 对属于该专家的子 batch：X^j(e)\hat{X}^{(e)}_jX^j(e)​
  • 局部计算：
    • H(e)=ϕ(X^j(e)W1(e))H^{(e)} = \phi(\hat{X}^{(e)}_j W^{(e)}_1)H(e)=ϕ(X^j(e)​W1(e)​)
    • O(e)=H(e)W2(e)O^{(e)} = H^{(e)} W^{(e)}_2O(e)=H(e)W2(e)​

将所有专家输出拼接为：

  • O^j∈RMj×Hdim\hat{O}_j \in \mathbb{R}^{M_j \times H_{\text{dim}}}O^j​∈RMj​×Hdim​（与 X^j\hat{X}_jX^j​ 一一对应）

4.4 Combine：all2all + unpermute + weighted_sum（送回并聚合）¶

目标：把专家输出返回到 token 的原属 GPU，并将 top-k 多路输出按权重聚合为一个 token 输出。

按来源 GPU 反向打包（pack-back）：

  • Dispatch 时每个样本带有其“来源 GPU + 来源 token 位置（src_slot）+ k_slot”
  • GPU jjj 将 O^j\hat{O}_jO^j​ 按来源 GPU 分桶：
    • 形成 sendbackj→i\text{sendback}_{j\to i}sendbackj→i​

第二次 all2all：

  • 所有 GPU 同时执行 all2all，GPU iii 收到所有返回样本集合 recvbacki\text{recvback}_irecvbacki​

本地还原与加权聚合：

  • GPU iii 对其本地每个 token ttt，收集来自 kkk 路的返回输出 Ot,1,…,Ot,k{O_{t,1},\dots,O_{t,k}}Ot,1​,…,Ot,k​
  • 按 router 权重聚合：
    • Yi[t]=∑r=1kwi[t,r]⋅Ot,rY_i[t] = \sum_{r=1}^{k} w_i[t,r] \cdot O_{t,r}Yi​[t]=∑r=1k​wi​[t,r]⋅Ot,r​

Combine 后的输出排布：

  • GPU iii 得到：
    • Yi∈RSP×HdimY_i \in \mathbb{R}^{\frac{S}{P} \times H_{\text{dim}}}Yi​∈RPS​×Hdim​
  • 输出仍是按序列维度切分（SP），可直接送入下一层。

五、全局数据流回顾¶

将各阶段的排布变化串联起来，便能看清整条流水线的”数据拓扑”：

阶段数据排布通信
qkv_linear 输入序列切分 (SP)，(S/N)×H(S/N) \times H(S/N)×H—
qkv_linear 输出（列并行）隐藏维切分 (TP)，S×(H/N)S \times (H/N)S×(H/N)无（本地计算）
方案一 out_linear（行并行）输出全量复制，S×HS \times HS×Hall_reduce
→ Slice 为 SP序列切分，(S/N)×H(S/N) \times H(S/N)×H本地切片
方案二 out_linear（行并行）输出序列切分，(S/N)×H(S/N) \times H(S/N)×Hreduce_scatter
方案三 all2all 后序列切分 (SP)，(S/N)×H(S/N) \times H(S/N)×Hall2all
→ out_linear（完整权重）输出序列切分，(S/N)×H(S/N) \times H(S/N)×H无
MoE Dispatch all2all专家分桶，Mj×HM_j \times HMj​×H（不均匀）all2all
Expert grouped_gemm专家分桶，Mj×HM_j \times HMj​×H无（本地计算）
MoE Combine all2all序列切分，(S/P)×H(S/P) \times H(S/P)×Hall2all

可以看到：三条路径都会将 Attention 层的 TP 激活”归还”为 SP，从而 MoE 层可以无缝地以序列并行为接口完成 EP 路由，整个前向过程不需要任何额外的同步等待（在理想的通信-计算重叠实现下）。

六、总结¶

  • 方案一（行并行 + all_reduce + slice）：实现最直接，权重内存占用低（1/N1/N1/N），但会先在每张 GPU 上拿到完整 ZZZ，通信和显存开销都相对更高。
  • 方案二（行并行 + reduce_scatter）：保留了方案一的低权重内存占用，同时把集合通信量压到方案一的一半，并直接输出 SP shard；但它仍需等待 out_linear 完成后才能开始归约，重叠空间有限。
  • 方案三（all2all + 完整权重）：按“每 GPU 单向发送量”统计，相比方案一的 all_reduce + slice，通信量只有 1/(2N)1/(2N)1/(2N)；相比方案二的 reduce_scatter，通信量只有 1/N1/N1/N。同时，由于它通信的是 out_linear 之前的 YYY，更容易和前面的 Attention 计算做细粒度重叠。代价是每张 GPU 需存储完整的 out_linear 权重。当 GPU 显存充裕、NVLink 带宽高、且下游对 SP 排布有明确需求时（如接 EP-MoE），方案三的优势更为突出。
  • EP 的 MoE 层：以 SP 排布为接口，两次 all2all 完成 Dispatch 与 Combine，实现专家参数的分片存储与正确的 token 路由，输出依然是 SP，可无缝接入下一 Transformer 层。

三者的联动使得超大规模 MoE 模型（如 DeepSeek、Mixtral 等）在多机多卡场景中既能充分利用 NVLink/IB 带宽，又能将每卡的参数与激活内存控制在可接受范围内。
